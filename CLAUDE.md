# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`shurl` is a URL shortener service with a package-by-feature architecture (see `apps/api/src/links/`). Persistence uses **Bun's `SQL` client directly (MySQL) — no ORM**; vendor lock-in to Bun/MySQL/Redis is an accepted tradeoff. Prefer Bun/Web-standard built-ins (`SQL`, `Bun.redis`, `Glob`, `crypto.getRandomValues`, `setInterval`) over adding new dependencies.

The repo is a **Bun workspaces monorepo** (`workspaces: ["apps/*"]` in the root `package.json`) with two apps today: `apps/api` (`@shurl/api`, the Hono backend) and `apps/web` (`@shurl/web`, the React frontend). New apps/services go under `apps/`; shared code, once there's more than one consumer, goes under `packages/` (doesn't exist yet — don't create it preemptively).

## Commands

This project uses **Bun**, not Node/npm.

- Install dependencies (from repo root): `bun install`
- Run dev server (hot reload): `bun run dev` — runs `bun run --filter '*' dev`, which fans out to each workspace package's `dev` script: `@shurl/api` (Hono, http://localhost:3000) and `@shurl/web` (Vite, http://localhost:5173). Bun's `--filter` accepts a workspace-name/path glob, so a specific app can be targeted directly, e.g. `bun run --filter '@shurl/web' dev`.
- Lint: `bun run lint` — runs `bun run --filter '*' lint`, fanning out to each workspace's own `lint` script. `@shurl/api` has its own `apps/api/eslint.config.mts` (ignores `dist/`, `@eslint/js` recommended + `typescript-eslint` recommended). `@shurl/web` has its own `apps/web/eslint.config.js` (React/JSX-aware: hooks, fast-refresh, TanStack Query rules) — each app's flat config is resolved independently, not merged with a shared root config (none exists).
- Format: `bun run write` (Prettier, writes in place, repo-wide) — one shared `.prettierrc` at the repo root covers both apps; `apps/web` has no `.prettierrc` of its own.
- Build the frontend: `bun run --filter '@shurl/web' build` (`tsc -b && vite build`); `@shurl/api` has no build step (`bun run src/index.ts` runs the TS source directly).
- Test: `bun run --filter '@shurl/api' test` — runs `bun test --isolate` for `@shurl/api` (`*.test.ts` files colocated with the source they cover, e.g. `apps/api/src/auth.test.ts`, `apps/api/src/links/links.service.test.ts`). `--isolate` (each test file gets a fresh module registry/global object) is required, not cosmetic: multiple test files use `mock.module()` to replace `./links.repository` with different fakes, and without `--isolate` those mocks race across files in the same process, since `bun test` otherwise runs all files in one process — so file B's `mock.module` call can clobber file A's before file A's `await import(...)` of the module under test resolves. `apps/api/test/setup.ts` (preloaded via `bunfig.toml`'s `test.preload`) seeds default env vars so the suite doesn't depend on a developer's local `.env`. `@shurl/web` has no test suite yet.

### Docker

- `docker-compose.yaml` (at repo root) runs the app (via `apps/api/Dockerfile.dev`) alongside a MySQL database and a Redis instance, with a file-watch sync of `./apps/api/src`. The build `context` is the repo root (not `apps/api`) so the image can install from the root `bun.lock`/workspace `package.json` files.
- `apps/api/Dockerfile` is the production image: installs with `--production` from the root lockfile plus `apps/api/package.json`, copies `apps/api/src`, runs as the `bun` user, entrypoint `bun run src/index.ts` (cwd `apps/api`).
- `apps/api/Dockerfile.dev` installs full deps the same way and runs `bun dev` as the `bun` user (cwd `apps/api`).

## Architecture

- `apps/api/src/env.ts` validates required environment variables at startup using a Zod schema (`envSchema`). If validation fails, it logs the error and calls `process.exit(1)`. Any new required env var must be added to this schema (and to `apps/api/.env.example`) or the app will refuse to boot.
- `apps/api/src/index.ts` builds the host-specific Hono apps (see the dispatch description below); `apps/api/src/app.ts` holds the shared middleware (request logging logs method/path/status/duration via `logger`, level based on status code) and `/health`/`/metrics`. `cors` (origin restricted via the `CORS_ORIGIN` env var, comma-separated) and `prettyJSON` apply to the admin app only.
  - Requests are **dispatched by Host** in `index.ts`'s default-export `fetch` (the `Host` header must survive any proxy). Three apps share the base middleware from `apps/api/src/app.ts` (`createBaseApp`: `requestId` → request logging → `secureHeaders` → Prometheus metrics, plus the global `onError`): `ADMIN_HOST` (env) → `adminApp` (`cors`, `prettyJSON`, `/health`, `/metrics`, and everything under **`/shurl/api`**: `/auth/links`, `/auth/domains`, `/docs`, `/openapi.json`); a host found in the `domains` table (via `domains/domains.registry.ts`'s synchronous in-memory `findDomainByHost`, refreshed every 30s and on local writes) → `redirectApp` (only `GET /:code`); any other host → `opsApp` (only `/health` and `/metrics`, so probes hitting a pod IP work). Because hosts never overlap, there are **no reserved short codes** and route registration order doesn't matter. The JWK auth middleware is registered on the inner `adminApi` router (scoped to `/auth/*`). The exported `AppType` (consumed by `apps/web`'s `hc` RPC client) intentionally reflects the **unprefixed** `adminApi` shape (e.g. `api.auth.links`, `api.auth.domains`) — the `/shurl/api` prefix lives in the client's base URL (`VITE_API_URL`). Don't import types from `'bun'` in `index.ts`/anything reachable from it: it leaks Bun's global `Response` augmentation into `apps/web`'s typecheck and breaks the `hc` client's `ClientResponse` typing.
  - `/auth/*` routes (now under `/shurl/api`) are protected by JWK-based JWT verification (`hono/jwk`), configured from `JWKS_URI`, `AUDIENCE`, and `JWK_ISSUER`. The verified payload is available as `c.get('jwtPayload')` (typed via `JwtVariables` from `hono/jwt`).
  - `apps/api/src/auth.ts` implements RBAC on top of the verified JWT: `JWT_ROLE_CLAIM` (e.g. `resource_access.shurl.roles`) is a dot-delimited path resolved against the JWT payload to find the roles claim (`getRoles`), which may be a single string or an array of strings — providers differ (Keycloak nests roles per-client, others use a flat claim). `hasRole(payload, ADMIN_ROLE)` checks for the `admin` role. `JWT_USERNAME_CLAIM` (default `preferred_username`) is the same kind of dot-delimited path, resolved via `getUsername`, used to snapshot the creating user's display name onto a link (see `owner_username` below) — unlike the roles/sub claims, it's informational only and never gates access. Any authenticated user can create/manage their own links; the `admin` role additionally grants both read and write access across all owners — `GET`/`PATCH`/`DELETE` on `/shurl/api/auth/links/{id}` and `GET /shurl/api/auth/links` all bypass owner-scoping for admins (see `links.routes.ts`'s `isAdmin` helper and `links.service.ts`'s `isAdmin` parameter, threaded down to `links.repository.ts`'s `updateLink`/`removeLink` as an `ownerScope: string | null` — `null` means "any owner"). The one thing admin does **not** override is **308 immutability**: a permanent link can't be edited or deleted by anyone, including admins.
  - `/metrics` (root path, not under the prefix — kept fixed for probes/scrapers; served on `ADMIN_HOST` and on unregistered hosts) is protected by IP allowlisting (`hono/ip-restriction`, restricted to loopback and private ranges — no token) and serves Prometheus metrics via `@hono/prometheus` (registered with `collectDefaultMetrics: true`). Caveat: `ipRestriction(getConnInfo, ...)` allowlists the **TCP connection's** source IP, not any forwarded-for header. Behind a reverse proxy/ingress (which typically connects from a private IP), this allowlist passes through _every_ external request. If the real deployment sits behind a proxy, keep `/metrics` off the public ingress (network-level protection) rather than relying on this allowlist alone.
  - `/auth/links/*` (management, requires JWT, identified by numeric `id`) and `/:code` (public redirect) are mounted from `apps/api/src/links/links.routes.ts`. Every link response (`links.routes.ts`'s `toDto`) includes `id`, `code`, `domain`/`domainId`, and `shortUrl` (`` `${domain.scheme}://${domain.host}/${code}` `` from the joined `domains` row).
  - `await migrate()` and then `await loadDomains()` run before the default export, so the schema is applied and the domain registry is populated on every boot before the server starts accepting requests.
  - The global `onError` handler is the single place HTTP status codes get decided for errors: `HTTPException` (framework/validation errors) responds via its own `getResponse()`; any `Exception` (see `apps/api/src/util.ts` below) is serialized as `{ code, message }` with its `suggestedStatus`; anything else is logged via `logger.error` and answered with a generic `{ code: 'E_INTERNAL', message: 'internal server error' }` 500.
- `apps/api/src/db/client.ts` constructs the shared `db` client explicitly via `new SQL({ adapter: 'mysql', allowPublicKeyRetrieval, url, max })`, sourced from `env.DATABASE_URL`, `env.MYSQL_ALLOW_PUBLIC_KEY_RETRIEVAL`, and `env.MAX_POOL_SIZE` — replacing Bun's implicit global `sql` singleton so the connection pool size and MySQL 8 `allowPublicKeyRetrieval` behavior (needed for some auth plugins) can be configured. Every module that talks to MySQL (`db.ts`, `links.repository.ts`) imports `db` from here rather than importing `sql` from `bun`.
- `apps/api/src/db.ts` exposes `migrate()`, which reserves a dedicated connection off the `db` client (`db.reserve()` — needed because the MySQL named lock `GET_LOCK`/`RELEASE_LOCK` pair is session-scoped) and applies numbered `.sql` files from `apps/api/src/db/migrations/` (resolved via `import.meta.dir`, so it's independent of process cwd) in order, tracking what's applied in a `schema_migrations` table (`reserved.file()` runs each file; nothing is templated in TS). **To change the schema, add a new numbered migration file** — don't edit an applied one.
- `apps/api/src/util.ts` defines `Exception`, the base class for all domain errors: `code` (a stable string like `E_NOT_FOUND`), `message`, and `suggestedStatus` (the `ContentfulStatusCode` the global `onError` handler in `apps/api/src/index.ts` should respond with). Domain errors are thrown as dedicated subclasses with a fixed code/message/status baked into their constructor (e.g. `CodeConflictException` in `links.repository.ts`; `LinkNotFoundException`, `LinkImmutableException` in `links.service.ts`) rather than being constructed inline — this keeps error-to-HTTP-status mapping out of the routes/service call sites.
- `apps/api/src/links/` (package-by-feature) implements the shortener:
  - `links.schema.ts` — Zod schemas/constants: allowed redirect statuses (`302 | 307 | 308`), the immutable status (`308`), and the short-code format. `createLinkSchema` requires a `domainId`; a code is unique per `(domain_id, code)`.
  - `apps/api/src/domains/` — same layering for the `domains` table (`host` unique, `scheme`; host is immutable, no PATCH). `GET /auth/domains` is open to any authenticated user (the link form needs it); `POST`/`DELETE` require the `admin` role (403 otherwise). Deleting a domain that still has links fails via the `links.domain_id` FK (`errno === 1451` → `DomainInUseException`, 409). `domains.schema.ts` rejects `ADMIN_HOST` as a domain host.
  - `links.repository.ts` — the only module that touches `db` (from `apps/api/src/db/client.ts`) for the `links` table (raw parameterized queries, no query builder). Duplicate-code inserts are detected via `SQL.MySQLError` with **`errno === 1062`** (Bun's MySQL adapter reports `error.code` as the generic `ERR_MYSQL_SERVER_ERROR`, not a MySQL-specific string like `ER_DUP_ENTRY` — the real MySQL error number is in `.errno`) and raised as `CodeConflictException`.
  - `links.service.ts` — business rules: short-code generation (random base62, retried on collision) or user-supplied alias, per-owner scoping (a link's `owner` is the JWT `sub`; access by a non-owner is treated as 404 via `LinkNotFoundException`, not 403, to avoid leaking existence), and **308 immutability** (update/delete on a `redirect_status = 308` row throws `LinkImmutableException` → HTTP 409).
  - `links.counter.ts` — the eventually-consistent access counter: hits accumulate in an in-memory `Map` (`recordHit`) and are flushed to MySQL every 5s (`setInterval`, unref'd) via a batched transaction; a failed flush puts the counts back for the next attempt.
  - `links.cache.ts` — two-tier cache for `resolve()`, the public redirect hot path: an in-process LRU (`Map`, capacity/TTL-bound, `L1_MAX_ENTRIES`/`L1_TTL_MS`) backed by a shared Redis tier (`Bun.redis`, the global singleton client, `L2_TTL_SECONDS`) so cache writes are visible across horizontally-scaled instances without waiting on L1 to expire. Caches both hits (`LinkRow`) and confirmed misses (`null`, to absorb code-guessing traffic) keyed by short code. `create`/`update` populate the cache with the fresh row; `remove` invalidates it. Redis errors on read/write/invalidate are caught and logged (`logger.warn`) rather than thrown — the cache is best-effort and callers fall back to `links.repository.ts`.
  - `links.routes.ts` — two Hono routers: `managedLinks` (CRUD, mounted at `/auth/links`, already covered by the global JWK middleware) and `publicLinks` (`GET /:code` → `c.redirect(url, status)`, mounted at the root, registered last so it doesn't shadow `/health`/`/metrics`/`/shurl/api/*` — see Routing above).

### Frontend (`apps/web`)

React + Vite + TanStack Router/Query + `shadcn/ui` (Tailwind v4). File-based routing under `apps/web/src/routes/` (route tree is codegen'd to `apps/web/src/routeTree.gen.ts` by `@tanstack/router-plugin`'s Vite plugin — **gitignored, regenerated on every dev/build run, don't hand-edit it**). `_auth/*` routes are gated by `enforceLogin` in their route's `beforeLoad` (`apps/web/src/routes/_auth/route.tsx`).

- `apps/web/src/env.ts` reads config from `window.RUNTIME_ENV` first (for container/runtime injection, e.g. `${API_URL}`-style placeholders swapped at deploy time), falling back to Vite's build-time `import.meta.env.VITE_*` — see `getEnv`.
- `apps/web/src/oidc.ts` wraps `oidc-spa` (`oidcSpa.withExpectedDecodedIdTokenShape(...).createUtils()`), exporting `useOidc`/`getOidc`/`enforceLogin`/`OidcInitializationGate`. `VITE_OIDC_USE_MOCK=true` swaps in a mock implementation (`isUserInitiallyLoggedIn: true`, no real IdP) for local dev — mirror this when adding new auth-gated UI so it still works against the mock. The decoded ID token schema also declares `resource_access` (client roles, keyed by client id) — populated by a dedicated "shurl client roles" protocol mapper on the `shurl` Keycloak client (`docker/keycloak/realm-export.json`), mirroring the `resource_access.shurl.roles` path the backend reads server-side (see `apps/api/src/auth.ts`). `apps/web/src/lib/auth.ts`'s `useIsAdmin()` reads that claim to gate admin-only UI (e.g. the Owner column in the links table) — this is a UI convenience only, never a substitute for the server-side `isAdmin` check.
- `apps/web/src/api.ts` is a typed `hc<AppType>` client (`hono/client`, base URL `API_URL`) whose `headers` hook attaches `Authorization: Bearer <accessToken>` from `oidc-spa` when the user is logged in — new API calls should go through this instance rather than raw `fetch` or a generic HTTP client, to keep request/response types in sync with `apps/api`.
- shadcn components live under `apps/web/src/components/ui/`; the `.claude/skills/shadcn` skill (project-local, only active under `apps/web/`) covers adding/customizing them — see `apps/web/components.json` and `apps/web/.mcp.json`.

## Environment variables

Defined in `apps/api/.env.example` / validated in `apps/api/src/env.ts`: `LOG_LEVEL`, `JWKS_URI`, `JWK_ISSUER`, `AUDIENCE`, `JWT_ROLE_CLAIM` (dot-delimited path to the roles claim in the JWT payload, e.g. `resource_access.shurl.roles` — see `apps/api/src/auth.ts`), `JWT_USERNAME_CLAIM` (dot-delimited path to a display-name claim, defaults to `preferred_username`; snapshotted onto a link as `owner_username` at creation time via `links.service.ts`'s `create` — see `apps/api/src/auth.ts`'s `getUsername`), `DATABASE_URL` (must be a `mysql://` or `mysql2://` URL — passed explicitly to `new SQL({ url, ... })` in `apps/api/src/db/client.ts`, not read implicitly by a global client), `MYSQL_ALLOW_PUBLIC_KEY_RETRIEVAL` (boolean, default `false` — passed as `allowPublicKeyRetrieval` to that same `SQL` constructor; needed for some MySQL 8 auth plugins), `MAX_POOL_SIZE` (positive int, default `10` — passed as `max`, the connection pool size), `REDIS_URL` (`redis://`/`rediss://`/`valkey://` — read directly by the global `Bun.redis` client used in `links.cache.ts`, not passed through explicitly), `CORS_ORIGIN` (comma-separated list of allowed origins, passed to `hono/cors`'s `origin` option), `ADMIN_HOST` (`host[:port]`, lowercased — the host that serves the admin app; see Architecture), `PUBLIC_BASE_URL` (optional, **legacy**: on boot `db.ts`'s `migrate()` exposes its host/scheme as MySQL session vars `@shurl_legacy_host`/`@shurl_legacy_scheme` so migrations `0004`/`0005` can register that domain and move pre-existing links onto it before `0006` makes `links.domain_id` NOT NULL — if links exist without it, boot fails). `/metrics` is no longer gated by a token env var — it's IP-restricted instead (see Architecture above). Bun loads `.env` relative to process cwd, which for local `bun run dev` (via `--filter`) and for the Docker images is `apps/api` — so `.env` lives at `apps/api/.env`, not the repo root.

`apps/web` has its own env file, `apps/web/.env.local` (Vite convention — not `.env`, and gitignored via `*.local`; `apps/web/.env.example` documents the shape): `VITE_API_URL`, `VITE_OIDC_USE_MOCK`, `VITE_OIDC_ISSUER`, `VITE_OIDC_CLIENT_ID`. These are build-time fallbacks read by `apps/web/src/env.ts`'s `getEnv` when `window.RUNTIME_ENV` hasn't overridden them at runtime. **`VITE_API_URL`/`RUNTIME_ENV.API_URL` must include the `/shurl/api` prefix** and use the admin host (e.g. `http://localhost:3000/shurl/api`, where `ADMIN_HOST=localhost:3000`) — it's used verbatim as the `hc<AppType>` base URL in `apps/web/src/api.ts`, and the API's admin/docs routes only exist under that prefix on `ADMIN_HOST` (see Architecture above). Locally, register a second domain such as `127.0.0.1:3000` (http) to try redirects, since `localhost:3000` is the admin host.

## Conventions

- No semicolons, single quotes, no arrow-parens on single params, 120 print width (see root `.prettierrc`, shared by both apps).
- Root ESLint config (`eslint.config.mts`, used by `@shurl/api`) extends `@eslint/js` recommended + `typescript-eslint` recommended. `@shurl/web` has its own `apps/web/eslint.config.js` layering React Hooks/Fast Refresh/TanStack Query rules on top of the same base (see Commands above).
- TypeScript `strict` mode is on in both apps. JSX: `apps/api` uses `hono/jsx` as the JSX import source (for any server-rendered JSX); `apps/web` uses the standard `react-jsx` runtime.
